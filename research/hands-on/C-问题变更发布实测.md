## ① 问题管理

| 验证项 | 结论 | 实测证据 |
|---|---|---|
| RCA 表单字段 | ✅ | 问题详情页有独立「分析」页签，含三块 RCA 字段：**影响明细（Impact）、根本原因（Root Cause）、症状（Symptoms）**，均可单独编辑并挂附件。路径：问题 → PB-1 → 「分析」页签。注意：新建表单（General Problem Template）本身**不含** RCA 字段，RCA 是建单后的后置动作。 |
| 新建问题表单字段 | ✅ | 提出人 / 影响 / 紧急 / 优先级 / 组 / 技术员 / 状态（默认 Open）/ 类别 / 项目 / 子类别 / 到期日期 / 关闭日期 / 受影响的服务 / 涉及的资产 / 涉及的CI / 标题 / 描述 / 附件（截图 C02-problem-add-form.jpg）。 |
| Solution / Workaround 字段 | ✅ | 问题详情「解决方案」页签内含**两个独立字段：变通方法（Workaround）与解决方案（Solution）**，分开编辑（截图 C03）。 |
| Solution/Workaround → Known Error 判定时点 | ✅（重要实测结论） | **「标记为已知错误」不受 Solution/Workaround 是否填写约束**：在变通方法、解决方案均为空的情况下，动作菜单中该项已可点击，弹出对话框「该问题是否为已知错误？是/否 + 评论」即可完成标记（截图 C04、C05）。判定完全由技术员手动决定，无自动判定时点、无前置条件。 |
| "Mark as Known Error" 可见范围与效果 | ✅ | 位于问题详情页顶部「动作」菜单（技术员视图）。标记后右侧属性面板出现独立字段「已知错误：是」，**问题状态保持 Open 不变**——已知错误是独立标志位而非状态值。动作菜单全量：添加注释 / 添加任务 / 从目标添加任务 / 添加提醒 / 添加时间明细 / **标记为已知错误** / 复制问题 / 删除问题 / 通知（发布公告、发送通知、通知事件请求技术员、通知事故用户）。 |
| **KEDB 是否对终端用户门户开放 ⚠（核心必核）** | ✅ 已核实：**不开放**（证实简报判断） | 设置 → 常规设置 → 用户门户设置：请求人门户可配置项仅覆盖**请求、服务目录、公告、解决方案（知识库）**；搜索设置原文"请求人门户将仅显示选择的模块的搜索结果"，可选模块只有 **公告 / 解决方案 / 请求模板 / 请求** 四项——**没有"问题"或"已知错误"模块**。门户设置全文检索无"已知错误/Known Error/KEDB"任何字样。结论：SDP Cloud 无面向终端用户的 KEDB，Known Error 仅供技术员内部使用；终端用户只能消费被发布为"解决方案"的知识条目。**这证实 KEDB 门户化是自研产品的真实差异化空档。** |
| 问题关闭代码 | ✅ | 设置 → 定制 → 问题管理 → 关闭代码，内置 5 个：Canceled / Failed / Postponed / Success / Unable to Reproduce。 |
| 问题关联模型 | ✅ | 问题详情「关联」页签固定四区块：**关联的事件请求**（添附/分离）、**关联的变更**（新建变更/添附/分离）、**因问题发起的发布**（新发布/添附/分离）、**由发布引发的问题**（添附）——事件↔问题↔变更↔发布互相关联是原生数据模型。 |

## ② 变更管理

| 验证项 | 结论 | 实测证据 |
|---|---|---|
| 内置变更类型清单 | ❌ 与资料不符 | 设置 → 变更管理 → 变更类型，内置 **4 类：Major / Minor / Significant / Standard**（各带颜色与描述）。**没有 Normal、没有 Emergency 类型**。资料"Standard/Normal/Emergency"口径不适用于当前云版；Emergency 改以**模板+独立工作流**形式存在（内置 Emergency Template / Emergency Change Workflow，类型标注"紧急"）。 |
| 变更模板 | ✅ | 内置 2 个系统模板：General Template（常规）、Emergency Template（紧急），创建人 System；可新建/复制模板。 |
| 状态机阶段数（6 还是 8） | ✅ **8 个阶段** | 设置 → 变更管理 → 阶段及状态（1-8/8）：**Submission → Planning（含上线/回退计划、检查清单、影响明细、停机）→ CAB Evaluation → Implementation → UAT → Release → Review → Close**（截图 C06-change-stages.jpg）。变更模板编辑器与变更详情页左侧阶段条均为同样 8 段。资料"6 阶段扩 8"的说法不准确——当前云版默认即 8。 |
| 变更管理配置子菜单 | ✅ | 变更类型 / CAB / 变更风险 / 变更原因 / 关闭代码 / 阶段及状态 / 变更角色 共 7 项。 |
| CAB / ECAB 多委员会 | ✅（部分相符） | 设置 → 变更管理 → CAB：默认 0 个，可「新建CAB」创建任意多个。新建表单仅 3 字段：**名 / 描述 / CAB成员（多选）**。**无独立的 ECAB（紧急咨询委员会）类型**——紧急委员会只能靠再建一个 CAB 实现。 |
| **5 种审批通过条件逐一核实** | ✅ 全部核实 | 变更详情 → 审批页签 → 添加审批级别 → 「规则」下拉，完整 5 项：**①任意人可批准 ②每个人需批准 ③首次响应动作 ④多数批准 ⑤% 批准（按百分比）**（截图 C09-approval-5-rules.jpg）。对话框其余字段：审批级别的名称、审批人（选择审批人）。 |
| 审批提醒定时器 | ⛔ 未发现独立定时器 | 全局「审批设置」页仅有：审批人变动时通知 / 按审批人自动批准 / 前置阶段已批准则后续自动批准 / 审批状态映射（待审批置 On Hold 停表、批准置 Open、拒绝置 Closed）/ 资源更新后重启审批。**未见"审批超时自动提醒/催办"的定时器配置**（通知规则中可能有审批通知模板，本次未逐一展开）。 |
| 变更表单字段（General 模板） | ✅ | Change Requester / 变更类型 / 回顾（Retrospective）/ 影响 / 紧急度 / 优先级 / 变更风险 / 地点 / 组 / Change Owner / Change Manager / 阶段 / 状态（默认 Requested）/ 状态备注 / 分类-条目-子分类 / 计划开始 / 计划结束 / 影响的服务 / 涉及的资产 / 涉及的CI / 变更原因 / 标题 / 描述 / 附件。模板编辑器含 角色权限 / 任务 / 表单规则 / 其他设置 页签。 |
| 变更工作流 | ✅ | 设置 → 自动化 → 工作流（模块=变更）：General / Emergency 两条，均为"全局： 显示所有阶段和状态"。工作流画布节点类型：**阶段 / 条件节点（条件、等待、切换）/ 动作节点（审批、通知、字段更新、任务、自定义函数、Webhook、计时器）/ 分支节点（分叉、联结）**。 |

| 验证项 | 结论 | 实测证据 |
|---|---|---|

| 阶段上限（12？） | ❓ 无法确认 | 支持新建自定义阶段与重排序，但未实测添加到 12 个以上验证上限。 |
| 状态三类型 | ✅ | 阶段和状态页可下钻每个阶段的状态列表（如 Submission 阶段内置 5 状态：Accepted / Rejected / Requested / Requested for Information / Submitted for Authorization，各配"通知角色"）。「新建发布状态」表单含**类型\*三选一：进行中 / 完成 / 拒绝**（即 In Progress / Completion / Rejection），另有通知角色与通知模板（主题/消息，支持 $ 变量）。 |

| 从变更发起发布的入口 | ✅ | 变更详情 → 「关联」页签 → **关联的发布** 区块，提供 **"新发布"（发起新发布）/ 添附（挂接已有发布）/ 分离** 三个按钮。变更关联面板共 7 类关联：关联的变更 / 由变更引起的请求 / 发起变更的请求 / 关联的问题 / 由变更发起的项目 / 发起变更的项目 / 关联的发布。 |

## ⑤ 事件→问题→变更 关联链路（实际操作）

✅ **已实际操作验证**（测试数据保留在系统中）：

1. **事件→问题**：问题 PB-1 → 关联页签 → 关联的事件请求 → 添附 → 选中事件 #1「【测试】Zia建单测试」（Open）→ 关联成功，计数变为 1。
2. **问题→变更**：问题关联页签「关联的变更」区块提供 **新建变更 / 添附 / 分离** 三个入口（可直接从问题发起变更）；反向地，变更 CH-1 关联面板也有「关联的问题」区块。
3. **问题→已知错误**：PB-1 已通过动作菜单标记为已知错误（属性面板"已知错误：是"）。
4. **问题→发布 / 变更→发布**：问题侧有「因问题发起的发布」区块（新发布/添附），变更侧有「关联的发布」区块（新发布/添附），双向可达。

链路结论：事件 ↔ 问题 ↔ 变更 ↔ 发布 四类单据两两关联全部由"关联"页签原生承载，且问题、变更均可作为发起端直接新建下游单据。
