# 模块D：SLA / OLA 与时间管理 —— ServiceDesk Plus 云版（中国区）实测

- 实测时间：2026-07-22
- 环境：ServiceDesk Plus Cloud 中国区 DC，Enterprise 试用（30 天），组织：河北恒讯达信息科技有限公司
- 入口：右上角齿轮 → 设置（/app/itdesk/AdminHome.do）→ 自动化 → 帮助台-服务级别协议（`/app/itdesk/AdminDetails.cc?forwardTo=sla`）

> 状态说明：✅已验证 / ❌与资料不符 / ⛔云版不可用或未找到 / ❓无法确认

## ① 响应+解决双时限配置界面 —— ✅已验证

路径：设置 → 自动化 → 帮助台-服务级别协议 → 新建服务级别协议（"新建事故SLA"表单）。

表单实测结构（截图 `D-05-sla-new-form-top.png`、`D-12-sla-101days-created.png`）：
- 名*、地点*（默认 Base Site，**SLA 按站点隔离**，列表页有"地点过滤"）、描述
- 服务级别协议规则：当有新的请求时 → ●根据匹配条件应用相应的动作（条件构造器）/ ○无条件加以应用（提示"SLA将会应用到所有入站的请求"）
- **符合上述规则的请求的响应时限**：天 / 小时 / 分（DOM id：`fr_due_by_days`）
- **符合上述规则的请求的解决时限**：天 / 小时 / 分（DOM id：`resolution_due_by_days`）
- 三个日历相关复选框：
  - `ignore-operational_hours` 不管是否为工作时间都应解决
  - `ignore-holidays` 应该解决，不考虑节假日
  - `ignore-weekends` 应该解决，不考虑周末

系统预置 4 个默认 SLA（High/Medium/Normal/Low），响应时间均为 0 天-0小时-0分，解决时间分别为 1/2/4/8 小时（截图 `D-04-sla-list-default4.png`）。另有"禁用所有基于邮件升级的SLA"批量开关。

## ② 升级机制 —— ✅已验证（⚠核心必核，矛盾已裁决）

**结论：响应升级 = 仅 1 级；解决升级 = 4 级。** "1级+4级"的资料正确，"各4级"的资料错误。

实测证据（DOM 元素 id 实锤）：
- "如果响应时间超过设定则升级：" 下仅有 **一个** `fresc-enable`（启用 一级 升级策略）
- "如果超过规定的解决时间则逐步升级：" 下有 `esc1-enable` / `esc2-enable` / `esc3-enable` / `esc4-enable` 共 **四级**

**Escalate Before/After 两种模式 —— ✅已验证**：每级升级均有 `before_after` 下拉，两个选项：**逾期后升级 / 逾期前升级**（截图 `D-07-escalate-before-after.png`，下拉展开实拍），后跟 天/小时/分 偏移量。

**升级动作全集 —— ✅已验证**（每级升级可配置）：
1. **升级到***（必选）：选择**机构角色和/或技术员**（截图 `D-06-escalation-level1.png`）——即改派人/改派角色
2. **自定义动作**两类（截图 `D-08-custom-action-types.png`）：
   - 通知
   - 字段更新：可更新字段共 16 类 —— 资产、分类、CI、**工作组**、影响、条目、**级别**、模式、**优先级**、请求类型、状态、子分类、**技术员**、模板、紧急度、附加字段（截图 `D-10-field-list.png`，DOM 提取实锤）

对照清单"改派组/改派人/提优先级/提Level"：**全部覆盖**——改派组=字段更新·工作组✅；改派人=升级到（机构角色/技术员）+字段更新·技术员✅；提优先级=字段更新·优先级✅；提Level=字段更新·级别✅。

## ⑥ Due By Time 100 天上限 —— ❌与资料不符（已推翻）

实测：新建测试 SLA【测试】SLA-D模块验证，解决时限填 **101 天**，客户端无拦截、服务端无校验，**保存成功**并出现在 SLA 列表（解决时间显示"101 天 - 0 小时 - 0 分"，截图 `D-12-sla-101days-created.png`）。

**"Due By 上限 100 天"在云版不成立**（至少 101 天可配）。上限是否存在于更大数值（如 365/999）未继续探测。

## ⑦ 新建测试 SLA 并验证 Due By 计算 —— ⏳部分完成

- 测试 SLA 已创建成功（无条件应用于所有入站请求、响应 0、解决 101 天、Base Site、状态启用）。
- 通过 UI 创建测试工单两次未成功（SPA 表单请求人选择器通过脚本操作后提交被静默重置，列表中未出现工单），Due By 实际落单值未取到。预置默认 SLA 均为小时级时限，可推断 Due By = 创建时间 + 时限（受工作时间/节假日/周末日历约束，除非勾选 ignore 开关），但**未拿到工单级实证，标 ❓**。
- **收尾处置**：测试 SLA【测试】SLA-D模块验证已在列表中**停用**（toggle 关闭，记录保留作证据），避免"无条件应用"干扰其他模块的工单测试。

## ③ 运营时间 / 节假日 / 特殊运营时间 —— ✅已验证

路径：设置 → 帮助台配置 → 工作时间（`/app/itdesk/AdminDetails.cc?forwardTo=ophours`）。

- 页面顶部两个 tab：**工作时间** 和 **特殊工作时间**（截图 `D-19-ophours-list.png`）——即 v15200 的 Special Operational Hours（可用于变更冻结期等场景）在云版存在。
- 列表带"所有地点"站点过滤器；预置 **Default Operational Hour**（描述原文 "Operational Hours configuration for all sites and groups"），今日 09:00-18:00，特殊工作时间 "-"。展开行可见：周一~周五 标准时间 09:00-18:00（9 小时）、周六/周日 非工作日。
- 点"新添"弹出"**新建运营时间**"对话框（截图 `D-20-ophours-new-form.png`）：
  - 名*、描述
  - **应用到*：选择地点（和/或）组** —— 运营时间按**站点（地点）和/或组**配置 ✅
  - 工作时间：全天 / 标准时间（起止时:分，自动算时长 9 小时），可 **+休息时间**（支持扣除午休）
  - 工作日：周一~周日逐行启用 + 每天可选"标准时间"类型
- **节假日组**为独立菜单：设置 → 帮助台配置 → 节假日组（`forwardTo=holiday_sets`，未逐页展开，入口确认存在）。
- SLA 表单侧印证：每个 SLA 可选"不管是否为工作时间都应解决 / 不考虑节假日 / 不考虑周末"三个 ignore 开关，说明运营时间、节假日、周末三套日历默认参与 SLA 计时。

## ④ SLA 计时冻结（等待用户回复暂停）状态映射 —— ❓未找到直接证据

新建/编辑 SLA 表单全文提取中**没有**"计时暂停/冻结/挂起状态"相关配置项；SLA 表单仅含双时限+日历开关+升级。计时暂停的状态映射在云版 SLA 配置界面中不可见（可能在"帮助台配置 → 实例设置"或状态定义处另有全局开关，本模块未逐层核实，标 ❓）。

## ⑤ OLA（每 SLA 最多几个 OLA、每 OLA 最多几组）—— ⛔云版未找到 OLA 功能

三处交叉验证均无 OLA：
1. 新建事故SLA 与 编辑事故SLA（High SLA，`/app/itdesk/ui/settings/sla/4882000000293098/edit`）表单全文提取：无任何 "OLA / 运营级别 / 组内" 命中，表单到"保存 取消"结束；
2. 设置中心搜索框搜 "OLA" → "未找到结果"；
3. 直接访问 `AdminDetails.cc?forwardTo=ola` → 报 "Incorrect input format for Forwardto field"（参数无效）。

**结论：云版（本 Enterprise 试用实例）SLA 体系中不存在独立 OLA 配置**，"每 SLA 最多 5 OLA × 每 OLA 5 组"及"组内计时考核报表"在云版无法验证。组级计时考核在云版只能依赖 SLA 升级动作（升级到组/角色）+ 报表模块变通实现，非 OLA 语义。
