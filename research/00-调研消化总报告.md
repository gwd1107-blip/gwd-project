# 自研 ITSM 服务台调研消化总报告

> 本报告是对 10 路并行调研简报（research/01–10）的综合消化成果，面向"自研一套基于 ITSM 体系、对标 ManageEngine ServiceDesk Plus 的 IT 服务台管理系统"这一目标，回答四个问题：SDP 到底是什么、我们要对标哪些功能、开源世界有什么可抄的作业、我们如何做出自己的风格和特点。

> ⚠️ **2026-07-22 实测修订说明**：第二阶段已完成 SDP 云版（中国区 servicedeskplus.cn，Enterprise 试用）7 个模块的上机实测。**`research/hands-on/00-实测总结.md` 为最新事实来源**，凡本报告与实测结论冲突处（SLA 升级级数、OLA、SQL 报表、LLM 选型、变更类型、Due By 上限等），一律以实测总结为准。本报告正文保留原始调研表述，冲突处在行内以"〔实测修正见 hands-on/00-实测总结.md〕"标注，第六节实测清单已逐条标注裁决结果。

## 一、对标产品全景：ServiceDesk Plus 的产品理念与功能地图

### 1.1 产品理念：一个底座，而非一堆模块

综合简报 01–04，ServiceDesk Plus（SDP）最重要的认知不是它"有多少功能"，而是它的架构哲学：**所有 ITSM 模块共享同一个"工单（Request）模型 + 可视化工作流画布 + 模板机制"底座**。事件、服务请求、问题、变更、发布五类单据，本质上是"同一个工单基类 × 不同表单模板 × 不同生命周期工作流"的组合产物。这一点与 ServiceNow 的 task 基表继承、GLPI 的 CommonITILObject 抽象、iTop 的统一对象模型完全一致——五大产品殊途同归，证明这是 ITSM 系统的"标准答案"。

SDP 的产品形态可以概括为四个同心圆：

- **内核：工单引擎**。三级分类树（Category→Sub Category→Item）、影响×紧急度优先级矩阵、任务拆分与依赖、工时记录、父子单关联与级联。
- **第二圈：自动化与 SLA**。业务规则（写入时同步执行的条件-动作）〔实测修正见 hands-on/00-实测总结.md：云版业务规则仅"创建后/编辑后/被删除"，无 pre-hook 时点〕、自定义触发器（写入后异步执行）、定时动作（延时补偿）〔实测：云版为「计划」= 定时调度 Deluge 函数〕、响应/解决双 SLA + 各 4 级升级链〔实测修正：响应 1 级+解决 4 级〕 + OLA 内部考核〔实测修正：云版无 OLA〕，外加可视化工作流编排全生命周期。
- **第三圈：ITIL 全流程与 CMDB**。问题管理（RCA、已知错误）、变更管理（六阶段状态机、CAB、变更日历）〔实测修正：云版默认 8 阶段、无独立 ECAB〕、发布管理（9 阶段流水线），全部单据可关联 CI 做影响分析。
- **外圈：体验与生态**。自助门户三件套（服务目录+知识库+工单追踪）、技术员列表/看板双视图工作台、四层报表体系（预置/向导自定义/SQL 查询/定时推送）〔实测修正：云版无 SQL 查询报表〕、多实例 ESM（最多 15 个实例+统一门户）、200+ 集成与 Zia AI。

### 1.2 版本与商业策略：用功能分层定价

SDP 以 Standard（$13/技术员/月）→ Professional（$27，+ITAM）→ Enterprise（$67，+服务目录/问题/变更/CMDB）三级切分，5 技术员以下免费、最终用户不限量。这个分层本身揭示了 ITSM 能力的"价值阶梯"：**工单+知识库是地板，资产管理是中段，全流程 ITSM+CMDB 是天花板**。同时它把服务目录、问题管理、变更发布做成 add-on 单卖（$1,195–$2,395/年），说明这些模块具有独立购买价值——自研排期时可以借鉴这种"核心先行、高阶后置"的商业化弹性。

### 1.3 SDP 的强项与软肋

**强项**：模块间数据天然打通（无需集成开发）；自动化分层模型教科书般清晰（表单规则→业务规则→触发器→工作流→定时动作）；审批引擎通用化（同一套多级审批复用于服务请求/变更/发布）；v15200 起收敛为统一 Request Workflows，并用 MCP Tools 暴露 AI 能力，架构持续演进。

**软肋（= 我们的机会）**：

1. **KEDB 缺位**：官方社区明确反馈 SDP 没有面向终端用户的"已知错误数据库"门户，Known Error 仅供技术员内部参考（简报 01）。
2. **AI 深度耦合 Zoho 生态**：GenAI 完整能力仅云端提供，LLM 选项限于 Zia/ChatGPT/Azure OpenAI，国产模型、私有化部署支持不明（简报 03）〔实测修正见 hands-on/00-实测总结.md：中国区已落地 Zoho 托管 Qwen3.5-35B + DeepSeek（禁用），无 ChatGPT/Azure、无 BYOK——"不支持国产模型"表述已不成立，差异点应转向 BYOK/私有化/可插拔/审计〕。
3. **本土化浅**：虽有简体中文界面，但 IM 入口是 Teams/Slack/Zoho Cliq，国内企业微信/钉钉/飞书依赖第三方插件或 Zoho Flow 绕行（简报 04）。
4. **UI 历史包袱重**：作为 20 年产品，配置体系复杂（GLPI 管理员需一周上手，SDP 类似量级），可视化画布虽有但信息密度高。
5. **许可证与定价维度**：按技术员+IT 资产节点双重计费，大规模部署成本不低——这是开源与自研产品的天然价格空档。

**读表结论**：

1. **没有单一开源产品能完整对标 SDP**。GLPI 强在 ITAM+CMDB 与多租户，iTop 强在 CMDB 驱动与流程严谨度，bk-itsm 强在流程引擎与自动化，Zammad 强在多渠道体验——每家都只覆盖了 SDP 功能地图的一个扇区。这正是自研整合的价值空间。
2. **发布管理是普遍短板**：除 SDP 外仅 heidsoft/itsm 宣称覆盖。若我们的目标用户有发布管理诉求，这是低竞争的差异化点。
3. **AI 是全场空白带**：商业产品里 SDP/Zia 已跑到前面，开源界几乎空白——AI 原生设计是最大的"换道超车"机会（详见第四节）。

## 三、开源产品可借鉴点汇总

### 3.1 GLPI —— 学它的"插件化边界"与数据模型抽象

- **统一对象基类**：`CommonDBTM` 通用基类 + `CommonITILObject` ITIL 抽象（工单/问题/变更共享参与者、状态机、时间线、审批），二十年可维护性的根基。我们应以此为工单域模型的设计原型。
- **关系优先**：任何对象可挂载到工单，影响分析靠通用关系表而非专门模块——"任意对象关联"应做成系统一等公民。
- **插件机制与"核心收编"策略**：hook + 目录约定 + Marketplace，官方持续把最流行插件（盘点、表单、自定义对象）内化进核心。启示：自研要划清"核心主干 vs 扩展长尾"的边界，并以 API 稳定性契约约束扩展点（GLPI 最大抱怨就是插件跨版本兼容性）。
- **双时钟 SLA（TTO/TTR）+ 日历引擎 + OLA 分离**：响应与解决独立计时、挂起自动补偿、时钟只在工作时间走——可直接照搬为 SLA 引擎规格。
- **Entity 树 + Profile 二维权限**：多租户/多部门隔离的成熟模式，递归/非递归授权。
- **增量盘点协议**：Agent 只上报变化字段，大规模终端下显著降负载。
- **反面教训**：配置复杂（管理员一周上手）、UI 信息密度高、大数据量性能需调优。

### 3.2 iTop —— 学它的"CMDB 驱动"与元数据架构

- **CMDB-first**：CI、工单、服务、合同、SLA 建在同一对象模型内，`Ticket↔CI` 多对多关联与 `CI↔CI` 依赖关系表必须一期建好，事后补丁必败。
- **状态机 + 字段约束矩阵**：每个状态下每个字段的隐藏/只读/必填由元数据声明（H/RO/M 矩阵），而非硬编码——做成配置表，既严谨又可配。
- **SLA 双计时器 + 挂起暂停 + 阈值变色**：75% 黄、100% 红、超时自动升级并留痕（deadline/cumulated/overrun），SLA 留痕直接服务报表。
- **父子工单级联解决**：核心设备故障引发工单风暴时，父单解决自动级联子单——实现成本低、价值高。
- **XML Delta 声明式定制**：扩展只声明与标准模型的差异，升级时定制自动保留。这是"低代码配置层"的最佳范式：核心模型稳定，差异配置随版本演进。
- **审批挂服务目录 + 免登录审批链接 + 超时默认动作**。
- **反面教训**：无自动发现导致 CMDB 数据腐化（"一年后成数据垃圾场"）——数据保鲜机制（同步/审计）必须一期考虑；UI 陈旧直接拉低用户满意度。

### 3.3 Zammad —— 学它的"多渠道体验"

- **多渠道收敛为单一会话线程**：客户跨渠道身份合并，"今天发邮件、明天发消息仍是同一条对话"。
- **SLA 语义教科书**：首次响应/更新间隔/解决三段时限 + 日历感知 + pending 类状态冻结 + 回到 open 按工单年龄瞬间重算升级——可直接作为我们 SLA 引擎的语义规格书。
- **自动化三层分离**：Trigger（事件）/ Scheduler（时间）/ Macro（手动批操作），且条件系统全站复用（过滤器、SLA、概览共用同一套 Object Conditions）。
- **Overviews（可保存过滤器视图）作为坐席主工作台**；agent collision 可视化（多人打开显示头像）；审计级工单历史。
- **反面教训**：Rails+ES+PG+Redis 四件套部署太重（≥4GB 内存），运维成本高——自研应控制部署依赖数量。

### 3.4 bk-itsm —— 学它的"流程引擎"与本土化集成

- **节点类型体系**：提单/人工/审批/会签/自动化（API）/子流程/判断节点，并行串行条件分支；自动化节点可"等待结果"挂起工单直到外部执行回传。
- **8 种处理人来源**：CMDB 角色、通用角色、指定个人、提单人、组织架构、前置节点变量、派单人现场指定、不限——这是中式企业审批文化的完整覆盖，远比 SDP 的指派模型灵活。
- **触发器三要素 + REST 回调带工单变量**（`${ticket.ticketId}` 内插）+ 触发记录可审计。
- **解耦哲学**：不自建自动化执行，走 OpenAPI/Webhook 对接外部编排平台与 IM——引擎应当开放，而非内置一切。
- **中文场景细节**：催办、督办、转单、回退（优先回退到处理组）、加签（商业版）——这些是国产用户的刚需语义，SDP 没有对应概念。
- **反面教训**：深度绑定蓝鲸 PaaS 导致部署门槛极高、安装复杂——自研把"开箱即用"做好就是直接反超。

### 3.5 Snipe-IT —— 学它的"资产出入库流"

- **六类对象模型**：资产/配件/组件/消耗品/许可（席位+到期告警）/套件，状态标签区分已部署/待部署/可部署/归档。
- **Check-out/Check-in 工作流**：指派到人/位置/资产，出库可要求签署 EULA、支持数字签名——资产领用合规闭环。
- **全量审计 + QR 盘点**：每个资产完整出入库历史，手机扫码直达资产页。
- **工单内嵌资产面板**（其 Jira 插件模式）：正是我们"工单关联资产/CI"的交互蓝本。
- **注意**：AGPL-3.0 有传染性，仅作功能参照或经 API 集成，不嵌代码。

## 四、自研差异化建议：做出自己的风格和特点

以下每条均按"对标现状 → 我们的做法"组织。

### 建议 1：AI 原生设计，而非 AI 外挂

**对标现状**：SDP 的 Zia 是后加的助手层，GenAI 完整能力仅云端提供，LLM 限于 Zia/ChatGPT/Azure 三家〔实测修正见 hands-on/00-实测总结.md：中国区已采用 Zoho 托管 Qwen3.5-35B，"国产模型支持不明"被推翻；但 SDP 仍无 BYOK、无私有化部署、无多模型并存、无 AI 审计——差异化表述应转向这四点〕，国内私有化与国产模型支持不明；开源产品（GLPI/iTop/Zammad）核心完全没有 AI。
**我们的做法**：从数据模型第一天起为 AI 预留位置——工单文本、处理动作、解决方案全部结构化沉淀为语料；AI 能力以"分诊建议、解决方案推荐、对话摘要、回复起草"嵌入工单处理主流程而非独立聊天框；LLM 网关可插拔（国产模型/私有化模型/OpenAI 兼容接口任选），按功能分别指定模型；借鉴 heidsoft/itsm 的"LLM 优先、低置信度降级关键词兜底"与"AI 审计留痕、高风险动作不自动执行"原则，让 AI 建议可追踪、可问责。这是全场（含 SDP 国内私有化场景）最大的空白带。

### 建议 2：中文体验与本土化合规优先

**对标现状**：SDP 中文界面是翻译层，IM 入口为 Teams/Slack，企微/钉钉/飞书需绕行第三方；催办、督办、加签、回退等中式审批语义缺失；国产数据库/信创环境适配无承诺。
**我们的做法**：原生支持企业微信/钉钉/飞书三类入口（IM 内建单、审批、处理工单）；流程引擎原生实现催办/督办/转单/回退/加签语义（bk-itsm 与嘉为商业版已验证这是刚需）；部署上适配国产数据库与信创 OS，提供 Docker Compose 一键部署与全离线安装包——直接打 bk-itsm"安装复杂"和 SDP"本土化浅"两个痛点。

### 建议 3：轻量现代化技术栈，部署即卖点

**对标现状**：Zammad 需 Rails+ES+PG+Redis 四件套（≥4GB 内存，官方自估月运维数百欧元）；bk-itsm 需整套蓝鲸基础平台；SDP on-prem 起步 4 核 16GB。
**我们的做法**：模块化单体 + PostgreSQL（JSONB 承载自定义字段、RLS 做租户过滤），搜索引擎前期用 PG 全文检索过渡、规模上来再切 OpenSearch；消息队列轻量场景用 Redis Stream；目标"2 核 4GB 可跑、Docker Compose 十分钟上线"的私有化交付体验。osTicket 证明了"单机能跑"对中小客户的吸引力，我们把同样的轻量带到全流程 ITSM。

### 建议 4：可视化管理画布，把"配置"做成产品亮点

**对标现状**：SDP 有工作流画布但信息密度高、学习曲线陡；iTop 社区版定制要手写 XML；GLPI 管理员需一周上手。
**我们的做法**：三块画布作为管理端核心体验——①流程画布（状态机节点+迁移守卫+审批节点，学 SDP Workflows 但用 React Flow 做更现代的交互）；②规则画布（Trigger-Condition-Action 可视化编排，带"测试中/生产中"状态与触发记录回放，补 Zammad 触发器无审计的课）；③CI 关系画布（拖拽建依赖、图谱上叠加未决工单/问题/变更数，学 SDP 关系图谱 + iTop 影响分析）。所有画布配置落元数据表（iTop XML Delta 思想），升级不丢定制。

### 建议 5：门户即"服务商城"，终端用户体验向消费级产品看齐

**对标现状**：SDP 门户是"服务目录+知识库+工单追踪"三件套，体验好但形态传统；iTop/GLPI 门户被批陈旧；SDP 的 KEDB 不面向终端用户。
**我们的做法**：门户做成"IT 服务商城"——服务卡片、购物车式申请、进度实时可视（物流式跟踪条）；知识库与已知错误库（KEDB）向终端用户开放，建单前强制语义推荐（AI 分流），补 SDP 的 KEDB 短板；内置 20+ 常见服务请求模板（账号申请/软件安装/网络接入/VPN/权限开通）开箱即用（heidsoft/itsm seed 模板思路），让客户第一天就有内容。

### 建议 6：SLA 引擎做成"语义最严谨"的单点长板

**对标现状**：各家 SLA 实现各有残缺——osTicket 只有关闭时限单维度；SDP 无"回到 open 按年龄重算"语义；iTop 无违约前多级预警动作（仅变色）；国产产品普遍无营业时间历。
**我们的做法**：集四家之长做一份完整语义规格：响应/更新/解决三段时限（Zammad）+ 营业时间/节假日历（GLPI/FeelDesk）+ 挂起暂停与恢复重算（iTop/Zammad）+ 违约前后各 4 级升级且升级可触发改派/提优先级（SDP）〔实测修正：SDP 实为响应 1 级+解决 4 级，且云版无 OLA——我们做全"各 4 级+OLA"反而超出 SDP 云版，见 hands-on/00-实测总结.md〕 + OLA 内部组级考核与全程留痕（SDP/iTop）。SLA 是 ITSM 里最容易被验收、最难做对的能力，做成单点长板性价比极高。

### 建议 7：开放集成架构，引擎不内置一切

**对标现状**：SDP 的 iPaaS 绑定 Zoho Flow；bk-itsm 证明了"ITSM 引擎 + 外部自动化平台解耦"的可行性但绑定蓝鲸。
**我们的做法**：全资源 OpenAPI + 事件 Webhook（带签名重试）+ 触发器动作内插工单变量调 REST 接口（bk-itsm 模式）；自动化执行节点可"等待结果"挂起工单；长期看齐 SDP v15200 的 MCP Tools 思路，把系统能力以标准协议暴露给外部 AI Agent——让客户的自动化平台（无论是 n8n、集简云还是自研）都能编排我们的服务台。

### 建议 8：ESM 多实例从简做起，预留企业级扩展

**对标现状**：SDP 最多 15 实例+统一 ESM 门户+按实例计费，是其企业版护城河；开源界只有 GLPI Entity 树可类比。
**我们的做法**：一期用"Entity 树 + Profile"二维模型实现部门/多租户隔离（GLPI 验证过的模式）；二期做统一门户聚合多部门服务目录（IT/HR/行政）；实例级模板化快速拉起（预置 IT/HR/设施模板）作为 V2 目标，不追求一步到 SDP 的 15 实例复杂度。

## 五、建议的模块蓝图与演进路线（MVP → V1 → V2）

依据简报 10 的架构建议（工单基类聚合根 + 四层模块划分 + GLPI 式权限 + 声明式元数据扩展）与其实施优先级（M1–M5），结合第二、三节的开源借鉴点，给出三阶段路线：

### MVP（对应 M1–M2，目标：可用的服务台）

**范围**：工单基类（Incident/ServiceRequest 两型）+ RBAC/Entity 权限 + 门户提单 + 邮件建单 + 基础业务规则 + SLA 引擎 + 服务目录/请求表单 + 知识库。

- 领域模型：Ticket 聚合根（状态、优先级、组、技术员、SLA、任务、备注、附件、历史全在基类）；优先级 = 影响×紧急度矩阵自动计算、禁止手填。
- SLA 引擎按建议 6 的完整语义一次做对（三段时限+日历+挂起+升级）。
- 规则引擎：Trigger-Condition-Action 存库配置化，覆盖建单路由、自动分派（轮询/负载均衡）、通知。
- 门户：服务目录+知识库+工单追踪三件套，内置种子服务模板。
- 验收标准：一个 5 人 IT 团队能用它完整承接全公司工单，含 SLA 考核与知识沉淀。

### V1（对应 M3–M4，目标：完整的 ITIL 全流程）

**范围**：问题管理（RCA/已知错误/Workaround）+ 变更管理（三类变更/分级审批/CAB/变更日历/回退计划）+ 审批流引擎（多级/会签/免登录链接/超时默认动作）+ CMDB（CI 类型/关系/影响分析画布）+ 监控告警接入 + 自动指派增强 + 报表仪表盘。

- 单据关联链（事件↔问题↔已知错误↔变更↔CI）原生支持，父子单级联解决。
- CMDB 数据保鲜：CSV/AD 导入 + 数据同步引擎接口（预留 GLPI Agent/监控对接），一致性审计。
- 报表四层：预置 + 向导自定义 + 定时推送 + 仪表盘 widget。
- AI 首批能力上线：智能分诊建议、解决方案 RAG 推荐、对话摘要（AI 审计留痕）。
- 验收标准：通过 ITIL 事件/问题/变更三大流程的完整演练；CMDB 影响分析可支撑变更评审。

### V2（对应 M5，目标：企业级与差异化放大）

**范围**：可视化流程设计器 GA + 资产全生命周期（出入库/EULA 签收/许可/采购 PR-PO/合同到期提醒，参照 Snipe-IT 与 SDP ITAM 闭环）+ 发布管理 + 多租户/ESM 强化（统一门户、实例模板）+ AI 全家桶（工作流辅助生成、变更风险预测、问题聚类）+ 移动化（企微/钉钉工作台全功能）+ 数据归档。

- 发布管理作为低竞争差异点（开源界空白）。
- 资产模块闭环：采购收货自动建资产 → 领用签收 → 维修 → 报废释放许可，合同/许可到期自动建单提醒。
- 验收标准：对标 SDP Enterprise 功能覆盖率达 80%+，且 AI 与中文体验两项明显超出。
