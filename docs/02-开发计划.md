## 一、开发约定（用户要求的硬性约束）

| 约束 | 规则 |
|------|------|
| **单文件 ≤ 1000 行** | 硬约束。任何源文件超过 800 行时触发拆分预警，按职责拆成多个文件 |
| **每轮交付 ≤ 1000 行** | 软目标。每轮新增+修改代码控制在 1000 行左右；超出则把该轮再拆成 a/b 两个子轮 |
| **代码解释标注** | 见第二节注释规范，目标是"非作者也能逐段核查" |
| **小颗粒迭代** | 每轮结束都是可运行、可验收的状态，不允许"写一半"的中间态提交 |
| **本地先行** | 全部在本地开发验证；企微对接轮之前不依赖任何外部账号；最终 Docker Compose 部署到用户公网服务器 |

## 二、代码与注释规范

### 2.1 文件头注释（每个源文件必须有）

```ts
/**
 * 文件：server/src/ticket/ticket.service.ts
 * 职责：工单核心业务逻辑（接单/处理/解决/关闭）
 * 对应设计：docs/01-MVP产品设计方案.md 第 3 节（事件管理）
 * 依赖说明：依赖 prisma 数据访问；状态流转规则集中在 ticket.state-machine.ts
 */
```

### 2.2 注释三原则

1. **业务规则必注**：凡涉及设计方案中的规则（状态流转、优先级计算、时限计算、级联解决），注释中引用设计文档章节号，如 `// 规则：待确认超 7 天自动关闭（设计 3.1）`。
2. **"为什么"优先于"是什么"**：不逐行翻译代码，解释决策原因和边界情况。
3. **公共函数必有 JSDoc**：参数、返回值、可能抛出的业务异常。

### 2.3 每轮交付物中的「人工核查指南」

每轮结束后，我会在回复中给出：
- 本轮变更文件清单（含每个文件行数、职责一句话）
- 3–6 个**核查要点**（指出应该重点看哪几段逻辑、预期行为是什么）
- 验证步骤（怎么亲手复现我验证过的流程）

## 三、技术栈（开工前请确认）

| 层 | 选定 | 备注 |
|----|------|------|
| 前端 | Vue 3 + Vite + TypeScript；企微端用 Vant 4，管理端用 Element Plus | 一个 monorepo 两个子应用 |
| 后端 | NestJS (Node 20 + TypeScript) | 模块化天然适配"每文件 ≤1000 行"的拆分要求 |
| 数据库 | PostgreSQL 16 + Prisma ORM | schema 即数据模型文档，迁移可追溯 |
| 缓存/队列 | Redis 7（会话 + 通知异步队列） | |
| 部署 | Docker Compose（app / web / pg / redis 四服务） | 与用户公网服务器部署目标一致 |
| 测试 | Vitest（后端关键规则单测）+ 每轮浏览器端到端走查 | 状态机、优先级、时限计算必须有单测 |

> 若团队更熟 Java，可整体换成 Spring Boot + MyBatis，计划结构不变。**默认按上表执行，有异议开工前提出。**

## 五、轮次拆解（9 轮，每轮含文件清单与行数预算）

> 行数为预算上限（含注释），实际会更少。标注 ★ 的轮次有强外部依赖。

### R0 — 项目骨架与开发环境（约 500 行）

**目标**：`docker compose up` 一键起全套环境；前后端能跑、能连通数据库。

| 文件 | 行数预算 | 职责 |
|------|---------|------|
| docker-compose.yml / .env.example | 80 | pg + redis + server + web 四服务 |
| server 骨架（main.ts / app.module / prisma module / 健康检查） | 200 | NestJS 启动 + `/health` |
| prisma/schema.prisma（仅 User/Department 两个 model） | 120 | 先建用户域 |
| web-h5 / web-admin 骨架（路由 + 布局 + 登录页占位） | 250 | Vite 双应用 |

**验收**：`docker compose up` 后访问 h5 和管理端均有页面；`/health` 返回数据库连通状态。
**核查要点**：compose 服务依赖与卷挂载；prisma 连接串环境变量化。

### R1 — 用户域 + Mock 认证（约 700 行）

**目标**：不依赖企微，用 3 个内置测试账号（员工/技术员/管理员）完成登录态，为业务开发解耦。

| 文件 | 行数预算 | 职责 |
|------|---------|------|
| user module（service/controller/dto） | 250 | 用户与部门 CRUD（内部用）、角色判定 |
| auth module（mock 登录 + JWT + 守卫 + 角色装饰器） | 250 | 登录发 token；`@Roles()` 鉴权 |
| seed 脚本（3 账号 + 预置分类，设计 3.4 六级分类） | 120 | 开箱数据 |
| 双端登录页 + token 存储 + 路由守卫 | 200 | 前端登录闭环 |

**验收**：三个角色分别登录，看到各自首页；无 token 访问 API 返回 401。
**核查要点**：角色判定逻辑是否与设计 2.3 一致；token 过期处理。
**单测**：角色守卫。

### R2 — 事件管理后端（约 900 行，若超拆 R2a/R2b）

**目标**：工单域完整 API，状态机严格按设计 3.1。

| 文件 | 行数预算 | 职责 |
|------|---------|------|
| prisma 增补（Ticket / TicketEvent / Category） | 150 | 工单模型 + 统一时间线表 |
| ticket.state-machine.ts | 120 | **五态流转表 + 非法流转拒绝**，纯函数易核查 |
| ticket.service.ts | 300 | 提单/接单/回复/挂起/解决/关闭/取消/转交 |
| ticket.policy.ts | 100 | 优先级计算（紧急度×影响面，设计 3.5）+ 时限推导 |
| ticket.controller + dto | 200 | REST API，入参校验 |
| 单测（状态机 + 优先级 + 时限） | 150 | 关键规则全覆盖 |

**验收**：API 层全状态流转可走通；非法流转（如待处理→已关闭）被明确拒绝。
**核查要点**：状态机转移表 vs 设计 3.1 图；解决时"解决方案必填"；时间线记录完整性。
**单测**：本轮回重点。

| web-h5：工单进度条组件（物流式跟踪） | 80 | 复用组件 |

**验收**：我用浏览器自动走通"H5 提单 → 管理端接单处理 → 解决 → H5 确认关闭"并截图；你按核查指南手动复现。

### R4 — 问题管理（约 800 行）

**目标**：事件升级问题、RCA 结构化记录、级联解决、已知错误标记。

| 文件 | 行数预算 | 职责 |

| prisma 增补（Problem / ProblemIncident） | 100 | |

**验收**：建 3 张同分类事件 → 升级为 1 个问题 → 标记已知错误 → 解决并级联，关联事件请求人视角状态正确。

### R5 — 知识库 + KEDB 开放（约 800 行）

**目标**：知识 CRUD、全文搜索、关单/问题一键沉淀、提单实时推荐分流。

| 文件 | 行数预算 | 职责 |
|------|---------|------|

## 六、执行方式约定

1. **每轮启动**：你说"开始 R1"（或我按确认连续推进），我按该轮文件清单实现。
2. **每轮收尾我必做**：本地跑通 → 浏览器自动验证核心流程并截图 → 输出"变更文件清单 + 行数 + 核查要点 + 复现步骤"。
3. **你核查后**给"通过/要改"，通过才进下一轮；要改我在当轮内修，不带入下一轮。
4. **行数红线**：我每轮自查单文件行数并汇报；任何一个文件逼近 800 行会主动说明拆分方案。
5. 计划中每轮的行数预算总和 ≈ 6250 行（含注释与测试），与实际会有出入，以功能完整性为准、以行数红线为约束。
